# 重み解決がこの方式で動く理由

weight 解決が `triple > double > single > base` になっているのは、より具体的な交点情報を優先しつつ、データが足りない場合でも生成を止めないためです。

もし常に single から見るなら、より具体的な組合せ知識があっても活かしにくくなります。逆に、triple や double しか許さないと、データ不足の stage でほとんどが失敗に近い挙動になります。階層的 fallback は、この両方を避けるための折衷です。

facet selection が逐次選択であることも重要です。AuspiQ は4軸同時の厳密最適化ではなく、順に候補を絞りながら最終 weight を重み付き抽選に使います。これは、柔軟性と実装可能性を優先した設計です。その代わり、candidate_map や weight data の質が選択結果に強く効きます。

この設計は、「最も理論的に美しい」よりも「現実のデータ量でも動く」を優先したものです。4 軸すべての交点に十分なデータがある前提なら別の設計もありえますが、実際には stage ごとの weight data は疎になりやすく、facet code の体系も均一ではありません。階層的 fallback は、その不均一さを受け止めるための仕組みです。

その代わり、結果の説明可能性は少し複雑になります。なぜその題材になったかを本当に追うには、selection と weight type の両方を見る必要があります。AuspiQ が `weight_selection` や `selection` を detail 出力に含めるのは、この複雑さを利用者や開発者が後から追えるようにするためです。
