# CLI と core を分離している理由

AuspiQ では、CLI の引数解釈と、実際の処理ロジックをできるだけ分けています。これは、使う人向けの表面仕様と、内部の実装判断を同じ関数へ押し込まないためです。

たとえば `commands/generate.py` は、CLI から受けた option を `GenerationSettings` に畳み込み、依存オブジェクトを束ねて pipeline を起動します。一方、生成の段階構造そのものは `generation_pipeline.py` にあります。この分離があると、設定解決や表示を変えても core 全体に波及しにくくなります。

完全な分離ではない部分もあります。`commands/predict.py` は比較的厚く、I/O、進捗表示、Batch API の取り回しを抱えています。それでも、どこまでが CLI 都合で、どこからが再利用したい core かを見分けやすくするために、この境界は保った方が保守しやすい構造です。

この分離には、テストしやすさと docs の整理しやすさという利点もあります。CLI 都合のオプション解決や表示分岐まで core に入ってしまうと、end-user 向け手順と内部仕様の境界も曖昧になります。AuspiQ の docs を audience-first で分けやすいのは、コード側にもある程度この境界があるからです。

一方で、AuspiQ は完全な clean architecture ではありません。`predict` では command 層が厚く、生成でも CLI 側に設定解決が多く残っています。したがって、この説明は「理想的に完全分離されている」という話ではなく、「責務を見分けやすくするために分離している」という話として読むのが適切です。
